# 音频调度与恢复约定

适用实现：`server/worker.mjs`、`scheduler.mjs`、`audio-delivery.mjs`、`audio.mjs`，及 `index.mjs` 的服务生命周期。这里记录当前行为；逐项验证见 `m0-m2-evidence.json`，不把模拟账号上限当作供应商承诺。

## 上限与设置

| 项目 | 当前默认和边界 |
| --- | --- |
| 期望并发 | 1；绝对范围为 1 至 8，界面只显示不超过受信开放上限的可用档位；持久化于 `settings.scheduler.desiredAudioConcurrency` |
| 账号／路由上限 | 缺少已验证配置时为 1；受信服务端 `routeConcurrencyCap` 最大 8；本机本轮完整实测通过到 4，8 路试点未通过 |
| 有效并发 | 期望值、路由上限、积压数量与字节许可的最小值 |
| 本地音频工作 | `localAudioConcurrency` 默认 1，受信配置最多 2 |
| 原生媒体进程 | 全服务共用 1 个进程槽，包括上传、校验、截图和渲染 |
| 发送间隔 | 默认 100 ms；受信 `audioStartIntervalMs` 可配置，测试可设为 0 |
| 响应与积压 | 每份响应最多 100 MiB；默认最多 8 个在处理 attempt、800 MiB 预留与已封存字节合计 |
| 参考缓存 | 默认最多 180 MiB 的 Base64 内容；活跃引用不驱逐，超限时未发送失败 |

启动环境的 `AUDIO_CONCURRENCY` 和 `AUDIO_ROUTE_CONCURRENCY_CAP` 分别给出初始期望和受信上限。已保存的期望优先。浏览器的 `PUT /api/scheduler` 只接受当前 `revision` 和期望值；助手不能提高账号上限。当前产品只有一个音频连接配置，所有音频入口属于同一资源组，没有额外的多路由配置系统。

提高并发只给原计划尚未发送的目标补槽；降低并发等现有请求自然结束。二者都不会新增 attempt、重发 POST 或改变声音份数。

## 领取、顺序与资源

1. 同章仍只允许一个活动制作任务。普通单句、组、场景、音色试音、声音候选都进入同一网络池。
2. 事务领取 `queued` 且未领取的 attempt，同时登记 `ownerToken`、准备阶段和任务运行状态。任何一个数据库写入失败都会回滚领取，不留下无 Promise 的占槽项。
3. 先给等待中的任务机会；交互试音／候选连续最多两次后，有后台等待就给后台一次。已经在途的请求不抢占。
4. 最终发送事务重新核对任务、停止、未决请求、版本、参考资格及授权额度。参考缓存命中不能绕过停用和文件变化检查。
5. 逻辑顺序使用冻结的 `ordinal`。新记录以目标的 `generationEpoch` 判断更晚尝试；无 epoch 的旧记录继续按既有持久插入顺序保护历史，不能靠时间戳或返回先后选版。
6. 完整原件封存后释放网络槽；本地整理进入独立有界队列。领取前按每份最多 100 MiB 预留，封存后改计实际字节，达到积压上限就停止补槽。
7. 每次收束从当前数据库中的 attempts 重算 `done/counts`，重启恢复也使用同一计数规则。一个请求结束不能替整个任务宣布结束。已关闭历史任务补回原件时保持旧任务终态。

## 阶段、期限与停止

| attempt 业务状态 | 当前阶段 | 含义 |
| --- | --- | --- |
| queued | queued / preparing | 尚未发送；可停止并释放未用预留 |
| sending | sending / receiving | 已进入发送边界／正在接收，不能假定免费取消 |
| sending | rawSealed / processing | 完整原件已有依据，继续本地处理 |
| success | registered | 产物登记完成，是否成为当前声音由业务版本规则决定 |
| failed | rejectedNotSent / rejected | 未发送拒绝／已有明确失败依据 |
| unknown | outcomeUnknown | 无法确定上游是否完成，可能已计费 |
| unknown | localRecoveryPending | 原件已完整收到，本地处理或登记尚未完成；沿用旧 status 兼容，界面必须解释可免费恢复 |
| stopped | stoppedNotSent | 本次没有进入发送边界 |

旧记录可以没有 phase，读取时沿用其原业务状态。用户放弃候选是单向决定，所有 worker／delivery 进度写入经 `saveAudioAttempt` 保留最新 `discarded`，旧异步快照不得把它擦掉。

等待响应头和接收响应体分别计时：`audioResponseTimeoutMs`、`audioReceiveTimeoutMs` 默认各 180 秒；既有 `config.timeout` 仍作为两者的兼容默认。接收期限从响应头返回后开始，本地处理不消耗网络期限。响应过大、类型错误、超时或正常完成后都清理接收控制器，不遗留已释放槽的下载。已发送超时／断流仍按 unknown 处理，绝不据此自动重发。

本地媒体进程的期限从取得进程槽后开始：常规默认 5 分钟，音频元信息检查 30 秒、完整解码 120 秒；截图原有较短期限继续生效。调用方可以提供有效的正整数期限，不能用 0 禁用。到期先终止实际子进程，再释放槽，不让忽略终止信号的进程继续占资源。

“停止后续”只禁止未发送项。已经发送的合法回执照常接收和登记；停止后的任务需要等它们及本地工作收束。401／403／明确额度问题暂停资源组；429记录可用的 Retry-After 并停止后续，不自动重发也不笼统宣称余额不足；502及断流没有确定未执行证据时保留 unknown。

## 原件、派生与免费恢复

- 接收文件先写 attempt 唯一 `.wav.part`。完整响应、长度、解码及文件 flush 通过后，写原子完成清单，再封存正式原件。可解码的 `.part` 本身不是完整接收证据。
- 清单只记录同目录文件名，项目改名或迁移无需改写清单。原件／派生的大小及 SHA-256 用于核对文件系统与数据库不能同时提交的边界，不作为额外业务审批。
- 纯人声才使用尾部规则。处理版另存 `.processed.wav`，记录来源、算法版本、切点、帧数、原因与结果摘要；原件保持收到的字节。场景、试音、候选不套用纯人声裁剪规则。
- 已完成派生只核验原件和配方，不按新算法重剪；未完成旧版本配方与现行算法不兼容时保留原件并停止本地恢复。没有原件的旧记录明确标为“历史原件未保存”。
- `recoverLocal(attemptId)` 只读取本地完成依据并补处理／登记；重复调用不产生新声音或模型请求。存在完整原件待本地恢复时，共享入队边界返回 `raw-received-local-pending`，`retryUnknown` 也不能把它变成另一次付费请求。
- 有界尾部维护只接受实际项目、章节与明确单元集合。免费预览保存真实版本、当前源音频及处理范围；执行逐项复验并保留原件。部分失败可以用原 scope 重试，`audios.maintenance.id` 识别成功项，只继续失败项。外部改动要求重新预览。

## 重启、关闭、维护和回退

| 重启时证据 | 动作 |
| --- | --- |
| queued / preparing，无发送证据 | 收束为未发送停止，不自动继续原批次 |
| 已发但只有 part／无可信完成依据 | 保留 unknown，不提升半截文件，不自动重发 |
| 完整原件及有效清单，登记未完成 | 免费补本地处理／登记，原字节与处理来源保留 |
| 已完成派生 | 校验并重用原配方，不重复裁剪 |
| 旧任务已结束，后发现完整原件 | 仅补历史；不复活任务、不抢后来选用的声音 |
| 已登记但计数未收束 | 从 attempts 重算当前活动任务的持久计数与终态 |

服务关闭先禁止新请求和派发，等适用的 HTTP 请求、助手步骤／附件、音频在途、本地处理、分析完成后才关闭数据库及运行标记。`getActivity()` 是观察入口，`stopAdmission()` 禁止补槽，`drain()` 等工作实际结束；保留 `running` getter 仅为旧调用兼容，不能据此推断整个服务都空闲。

迁移、改名、删除、尾部维护需复用服务层活动检测和精确作用域，不从模型执行任意目录或 CLI。失败的迁移保留原工作区并恢复原助手服务；附件落盘与项目删除互锁，落盘完成仍重查会话归属。

离线备份须先正常关闭服务，使用已有 `scripts/backup.mjs create/verify/restore`，整体保存数据库及全部引用文件。新清单、原件、派生、助手附件原图／处理图均计入；有摘要的附件验证实际内容，旧附件缺少原图摘要会明确报告只能验证其大小，不能补造原始摘要。恢复到新目录，保留来源。

数据库语义版本为 4；旧写入器不能打开新语义库继续修改。默认回退办法是在新版本中将期望并发设为 1，保留原件、恢复及助手账本语义。若必须回退程序，应恢复与旧程序匹配的整份备份，不能让旧 worker 直接写当前数据库。

已验证的是本机 Mock 与真实文件／FFmpeg／SQLite，以及实际 SIGKILL 子进程恢复；断电保证、真实账号并发与语义听评不在这些证据内。
