# 配音工作台：定稿方案执行偏差审计与整改验证

日期：2026-09-25\
审计对象：当前本地工程；产品版本 v0.1，业务依据 v0.2.1 定稿补订版。\
结论性质：代码整改与工程验证记录，不是整套产品及声音效果的最终验收。

## 1. 结论与责任归属

用户的怀疑有依据。小说转剧本受阻，不能只归因于供应商限流或模型能力。原实现确实偏离了已经定稿的方案，而且这些偏差直接放大了模型偶发错误和服务限流的影响：

1. 方案要求有问题时保留有效草稿、指出具体缺口，原实现却把局部错误升级成整轮失败，缺少可用的局部修正和继续入口。
2. 方案要求程序提供原文块／区间、模型负责标注，原实现却额外要求模型重新抄写引文，再对抄写结果做逐字校验。这增加了方案没有要求的失败条件。
3. 方案要求优先理解完整章节，原实现把 4,446 字的第一章切成 203 块、分 9 次请求，其中 54 块只有空白。切块是定位手段，不应自动变成大量远端调用。
4. 自动检查曾经更多验证“出错后拒绝接受”，没有充分验证“保留成果、定位问题、局部校对、明确采用”的完整用户流程。测试通过因此未能证明方案已经正确落地。

上述问题属于执行与验证不足。本轮保留 v0.2.1 的业务方向，直接整改工程，未要求用户再次修改方案来迁就实现。

**整改后，使用默认的 gemini-3.8-flash，对授权的前两章各调用一次，均生成可采用草稿；两章采用后的正文与原文逐字一致，缺口和重复均为零。第一章还通过 Chrome 实际完成了局部修改与明确采用。当前这两章上的提取阻塞已解除。**

不能据此断言供应商今后不会限流，也不能把文字覆盖正确等同于角色、情绪或声音质量通过。

| 问题 | 定稿要求 | 整改后的行为 | 主要证据 |
|---|---|---|---|
| 局部错误导致整轮失败 | §3.1、A02：保留有效草稿和原文，指出具体缺口 | 每条独立记录问题；正确条目保留。显示缺失块、重复覆盖及越界，错误未修正前不能作为完整剧本采用 | `server/analysis.mjs`；局部错误、缺口、重复自动检查；Chrome 修正案例 |
| 强制模型重抄引文 | §3.1、§3.4：引用程序提供的块／区间 | 模型返回 `evidenceRefs`；程序提取出处及初始朗读正文，不再以模型抄写引文作为必经条件 | 两章真实请求与响应；非法引用检查 |
| 空白块及过度分批 | §3.2：优先完整章节理解 | 空白并入相邻原文块，保留空白文本和位置；普通章节一次请求，较长输入才按正文边界分批 | 第一章 149 块、零纯空白块、一次请求；Unicode 自动检查 |
| 无法只继续未完成部分 | 保留成果、故障恢复与明确操作原则 | 批次持久化；继续默认只处理未完成批次；重做已接收批次须明确替换；结果不明须明确确认可能重复计费 | 第二批模拟 429 后继续，仅补发剩余批次 |
| 重启丢掉已收到的响应 | 持久化与恢复原则 | 响应先保存，再解析；重启可从已保存响应恢复，零额外模型调用；在途未知请求不自动重发 | 重启恢复自动检查 |

| 草稿并发编辑与后批依赖不清 | §3.4、C03：相关修订一致后才采用 | 草稿编辑校验自身修订；采用同时核对章节和项目文本上下文；前批身份变化使依赖它的后批待重新分析，保留旧内容供查看 | 过期保存、项目上下文、前后批身份检查 |
| 新角色可能按同名混同 | §4、A10：同名不等于同人 | 已有角色用稳定 ID；新角色用本轮身份标识，显示名不充当唯一身份键；采用不默认替用户确认角色 | 同名两身份检查；真实第二章复用三个既有角色 |

### 当前实现的适用范围

- 当前按约 12,000 个 JavaScript 字符组织一次文本分析输入，长章再分批，提取时携带相邻 4 块上下文。这是输入组织的经验值，**不是输出 token 上限，也不是已验证的供应商最大上下文容量**。
- 请求不发送 `max_tokens`、`max_completion_tokens` 或工具设定的推理预算。不因本轮整改重新引入用户反对的输出限制。
- 请求仍有网络超时处理；超时可能已计费，记录为结果不明，等待明确操作。不存在“无限自动重试”。
- 有效草稿可以包含仍待人工核对的角色解释；完整覆盖只能证明文字没有被遗漏或重复，不能证明解释正确。
- 收到的响应和请求参数可追溯，诊断记录不保存 Authorization。服务返回文本会做密钥脱敏。

## 4. 基础首版其他执行偏差与整改

本轮没有只修文本入口，还回查了下游规则。

| 对照项 | 发现的缺口或风险 | 本轮处理 |
|---|---|---|
| 原文与修改沿革，§3.1—3.2 | 原始导入信息及显式改字、删空的记录不充分 | 保存导入原始文本和文件名；朗读修改保留编辑沿革；删空明确记为排除，退出朗读编排；覆盖校验拒绝旧来源版本 |
| 拆合继承，C01 | 实际模型未完整进入片段配置和比较；位置相关表演指导可能未经重新分配继承 | 拆分继承实际音色、数值、模型及模板；合并比较这些配置并展示差异；已有表演指导要求明确分配／确认；结构编辑保留父记录、修订和拆分位置 |
| 模型与音频匹配，§7、C06 | 设置变化可能使实际请求模型与保存的依据不一致 | 模型固定到片段和生成尝试，工作线程按尝试记录发送；模型进入匹配及检查依据；旧记录缺省按原 Seed 模型兼容 |
| 参考素材，§8.1 | 已导入参考文件后来损坏，仅文件存在不足以证明可发送 | 发送前实际解码检查，并再次核对素材资格；损坏参考不提交远端，不产生测试中的额外调用 |
| 原文更换与人物依据，§3—4 | 旧章原文替换后，旧出处支持的人物事实仍可能进入后续分析 | 原文明示事实保存来源版本；旧版本事实暂不进入模型上下文，界面提示复核。用户补充仍按适用章节保留 |
| 角色事实，§4 | 性别资料的明确编辑入口不足 | 增加本章起生效的性别字段，未知保持未知；与用户保存的事实来源一起记录 |
| 干声提示冲突，§8.1、§17.6 | 干声模式与明确要求额外音乐/音效的指导可能一同提交 | 保存指导不被偷偷改写；预览提示明确冲突，生成前要求处理。采用保守关键词检查，不宣称任意自然语言语义检测 |
| 编辑修订，C03/C04 | 间隔更新未完整推进相关修订 | 更新章节编辑与编排修订，旧播放会话随编排变化失效；单条音频不因此重跑 |
| 默认间隔，§10.3 | 缺少全局默认入口 | 设置可填默认间隔，供新章节继承；已有章节的实际间隔保持独立，服务端拒绝非法值 |
| 静音断点，§9.2 | 间隔中的断点可能关联到前条 | 间隔断点归下一条，重新编排后按稳定片段定位 |
| 母版完成与播放，§9、A22 | 后台准备结束触发自动播放 | 改为提示“已准备好”，等待用户点击；已有有效母版在用户主动点击试听时正常播放 |
| 母版损坏，§10.2 | 缓存记录存在或文件存在不等于内容可用 | 复用前检查解码和预期帧数，损坏时从已有音频本地重建；播放错误提供重建路径，不自动提交 TTS |

原有正确路线继续保留：稳定角色与显示名分离、单条覆盖保护、检查状态绑定实际音频及审核依据、章节服务端只读、命令去重、未知结果不盲目重试、参考停用与删除等待、已有音频本地导出、单一编排母版、最近通过版本保护、备份不覆盖原目录。

## 8. 当前还存在什么问题

1. **供应商可用性没有被永久证明。**历史 429 真实存在；新流程减少不必要请求，并能保存、恢复成果，但不可能消除供应商的限流、额度或路由波动。
2. **尚无证据证明旧 3.8 失败由预算导致。**历史去掉工具输出上限后仍出现 429；本轮无输出上限的两次成功只能证明当前整改路径能完成这两章。
3. **分段和导演建议仍需要审阅。**第一章有较长的连续旁白；约 300 字属于模型提示建议，不是程序硬切或已经保证的长度。可按声音制作需要手工拆分，并确认表演分配。
4. **超长章仍有实测边界。**已验证两章约四千字样本和模拟多批恢复。更长小说章节、非常庞大的角色上下文、其他模型的真实多批效果尚未覆盖；导演建议在分批时仍携带整章来源，极长章的输入效率需另行实测。
5. **旧失败记录不会凭空变成可恢复草稿。**此前版本未保存足够批次结构的记录只能作为历史查看；新一轮使用整改后的流程。不能从未保存的数据恢复原始模型成果。
6. **声音质量未完成验收。**本轮没有新增全文 TTS，不宣称音色一致性、漏字增词、情绪自然度或混音效果通过。

现在可以继续从新草稿完成角色核对、绑定实际声音和小批量音频制作。当前提取问题应从“工具已经卡死”更新为“前两章工程链路已跑通，进入人工语义与声音效果验收”。
