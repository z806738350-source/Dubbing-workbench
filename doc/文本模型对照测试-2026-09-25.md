# 文本模型对照测试

日期：2026-09-25，北京时间。用户授权使用《不要乱碰瓷》第一章和真实 Kunpo API 进行付费测试。

## 结论与修改

失败有不同原因，不能统一称为限流，也不能仅凭一次失败认定模型不可用。

- 供应商可用性：此前 `gemini-3.8-flash` 的完整第一章任务在完成 4/9 批后收到 HTTP 429、`rate_limit_error / Resource exhausted`。本轮同样观察到 429，但相同参数后来成功，属于非稳定复现的上游拒绝。
- 工具格式兼容：`gemini-3.6-flash` 曾返回顶层数组，以及由单反引号包裹的 JSON。内部标注可以解析，但工具原先只接收 `items` 对象和三反引号代码块。已兼容这两种外层包装，仍逐项检查正文覆盖、角色与出处；不修补或猜测 JSON 内部内容。
- 工具输出上限：原先固定 `max_tokens: 5000`。实测部分响应将推理计入预算，导致正式 JSON 未生成或被截断。曾以 10000 做对照；按用户最终要求，**正式工具已彻底移除输出 token 上限及其配置，不发送 `max_tokens`，采用服务商规则**。
- 模型内容正确性：接口成功、JSON 可解析与全文校验通过是不同阶段。`gemini-3.6-flash` 全部批次返回后，仍有两条引文与原文不一致，不能作为已通过的剧本采用。

## 方法

复用实际 `createAnalysis` 分批流程、提示词和角色上下文，在独立数据库副本中执行；正式项目、片段、默认模型选择均未修改。整章共 9 批，每批最多 24 个原文块或约 1200 字符，逐批串行发送。

修复格式兼容后重放已保存的成功响应，只继续尚未成功的批次，避免重复付费。因此这里的“9/9 批返回”是原始响应重放加后续真实调用的组合验证，不是一次全新独立的九批测试。重放逐项比较请求，允许输出上限变化，其他字段必须一致。

请求和响应记录保存在本机 `data/live-smoke/model-comparison/`；不保存请求头与密钥。没有获取服务商账单，不能把请求次数等同于实际计费次数。

## gemini-3.8-flash：输出上限是否导致 429

使用同一第一批正文、角色、提示词、温度和 JSON 模式，只改变是否发送 `max_tokens`，先正序后倒序执行：

| 顺序 | 参数 | 结果 | 耗时 |
|---|---|---|---|
| 1 | max_tokens = 5000 | HTTP 429 / rate_limit_error | 0.7 秒 |
| 2 | 不传 max_tokens | HTTP 200 / stop，覆盖检查通过 | 9.6 秒 |
| 3 | 不传 max_tokens | HTTP 200 / stop，覆盖检查通过 | 9.0 秒 |
| 4 | max_tokens = 5000 | HTTP 200 / stop，覆盖检查通过 | 4.4 秒 |

**相同的 5000 参数既失败也成功，不能断言它必然导致 429。** 无上限的两次成功也不足以证明参数与供应商额度预检查完全无关。要确定上游拒绝的内部原因，需要供应商日志或说明。不能将 429 直接解释为输出已达到长度上限；长度截断的直接证据是 `finish_reason: length`。

对照记录：`gemini-3.8-budget-1790267493446/`。

随后在实际整章流程中不发送 `max_tokens`，复用首批成功响应，再真实请求后续批次：第 2—5 批均成功，第 6 批仍收到 HTTP 429 / `Resource exhausted`，停止于 5/9。这进一步确认：**移除工具输出上限不能消除当前供应商的 429 问题**，但避免了工具主动施加 5000 token 截断条件。记录为 `gemini-3.8-flash-1790267625857/result.json`。本轮未循环重试、未采用部分草稿。
