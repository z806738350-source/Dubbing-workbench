## 0. 本轮边界：只有模型原生联合生成这一条路线

用户已经明确：看中的是 **seed-audio-1.0 一次生成自带背景音乐、环境和音效的完整结果**。本轮任务是查明并修复工作台对这项能力的限制、遗漏、错误转译或错误呈现。

**不实施：**独立背景生成后拼合、本地混音、音源分离、素材库兜底、增益滑块补偿、自动换其他模型、用新的制作模式掩盖原生场景的问题。之前讨论的本地分层方案撤回，不是本计划的第二阶段或备用路线。

**允许的本地处理仅用于取证和忠实播放／既有导出：**保存、解码校验、同文件比较、必要的格式转换及诊断。不得向原结果补声音后宣称模型原生背景已恢复。

本计划采纳不等于授权新付费调用。默认真实调用为0；实验先提交冻结的次数、用途、正文、参考、模型和路由范围，获得授权后再执行。

### 0.1 交付目标

用户在现有“声音背景”中描述并采用山洞水滴回响、仙侠旋律随后宁静后，工具应将完整、无自相矛盾的场景要求交给seed-audio-1.0；**供应商原始返回文件本身**应能辨识这些声音，同时保留正文与角色。

用户不需要学习分轨或后期操作，不增加一串人工确认，不要求每个声音事件自行配写技术提示。自然声景组织交给模型，程序负责意图保真、实际请求、费用和产物追踪。

### 0.2 本轮实际审计范围

已读取固定提交的交接说明、完整模板及关键analysis、enhancement、experience、worker、audio代码，核对原厂公开能力说明与当前Kunpo接口。原模板实际执行的六项观察性检查两轮均通过，说明代码确实加入了下述默认指令；它们**不是六项听感测试，也不是模型效果修复通过**。

未取得本次93.4秒WAV、27秒参考和原始私有请求日志，因而尚未听评、未确定声学根因的唯一归属；没有全量重跑408项或构建，没有修改仓库、用户库、main或NBchitu/layerforge。

一些早期附件已过期，需要逐份复查时应重新上传对应文件。本计划核心依据来自已取得的固定源码与当前交接，不因旧附件过期而阻止执行。执行者可以在本机先检查真实音频，不必公开小说、参考或密钥。

## 1. 审计判断：已经找到什么，尚未证明什么

### 1.1 模型能力与本产品限制要分开

原厂把“场景”作为共同组织角色表演、环境和声效的创作单位，而不是只把语音当作独立片段。[W01] 用户坚持原生联合生成与这一方向一致。

不能从“当前模板的一次结果听不清”推导模型做不到；也不能从官方演示或能力声明直接保证本路由、当前参考与长文本一定成功。应以同模型、同路由的完整场景对照定位。

### 1.2 确认的源码问题／限制

|编号|当前实现|审计定位|结论等级|
|---|---|---|---|
|N-F01|scene-v2无条件附加“对白时适度降低背景声音”，并附“不延长停顿”|`templates.mjs::compileUnit`|**确认的系统默认**，即使用户没有要求压低也存在；对本次声音的因果强度待A/B|
|N-F02|场景沿用共同的对白模板骨架；单旁白在无共同指导时仍收到“轮流说话，不重叠”|同上|**确认的不合任务默认**；不应把对白轮次规则写得像全场声景不得并行|
|N-F03|普通extract/director分析指令固定为“逐条干声”，禁止环境／音乐及额外留白|`analysis.mjs::instruction`|**确认的纯人声策略**；原纯人声场景合理，不能不区分地作为后续原生scene的创作总政策|
|N-F04|scene建议请求中的unit只带id和members；建议快照保留已有adopted事件，却没有保存并发送该unit的scene共同指导|`analysis.mjs::start/launch`|**确认的场景建议上下文缺口**。是文本建议支路遗漏，不是最终音频请求漏了guidance；手工已采用事件的本次案例不能据此认定直接根因|
|N-F05|连续环境与音乐最终被压为逐条事件说明，单个343字成员内部通常只剩“第1条正文期间”等粗粒度关系|`templates.mjs::anchor/events`及输入结构|结构保留语义位置，但没有独立组织完整声景与段内发展；“随后宁静”仍可由模型理解，不能说粗锚点必然导致失败|
|N-F06|参考、text_prompt和整体audio_config通过既有audio/speech路由发送|`worker.mjs`与网关文档|当前未发现用了错误接口或需要补某个隐藏“启用背景”开关；继续核验实际线上请求，而非凭端点名字猜测|

**优先级判断：**首先调查系统自动加的声音主次／节奏政策与场景输入组织，其次补scene建议上下文；参考影响、长输入及上游路由作为受控变量。不能先把问题变成“缺一个本地音量旋钮”。

### 1.3 两个必须避免的误判

**误判一：scene-v2混入了干声末段禁音乐。**实际模板scene分支没有该段，交接也核对了实际请求。不能为了得到一个简单根因而把dry-v1文字硬算到scene-v2上。[G01][G02]

**误判二：一切约束都要删掉。**不改写正文、不串角色、只用当前采用事件、按授权提交、保留unknown和历史，是正确边界。要删除／作用域化的是程序自加的创作偏好，而不是这些数据与费用保护。

## 2. 逐项解释：工具怎样可能把模型收窄成TTS

### 2.1 声音主次不是用户要求，却成为每次场景的固定政策

scene-v1明确把声音事件设为次要；scene-v2虽然增加“清楚可辨”，仍把“对白时适度降低背景”作为固定指令。scene-v2的这些文字不是根据本次用户要求选择的。

六项编译检查还覆盖了自拟反例：当用户共同指导明确表示背景正常可辨、不刻意压低时，编译输出**同时保留这份指导与固定的降低指导**。这证明模板没有协调显式意图和默认政策；不证明实际用户这次也输入了这个反例。

修复方向不是在尾部再加一句“请特别特别清楚”，而是让scene编译器不再无条件制定背景降低策略。用户明确要很轻的背景时保留；用户要清楚或正常时按其原意；未规定比例时交给模型自然组织，而不是默认为持续压低。

### 2.2 “不延长停顿”是节奏偏好，不是正文保真

没有增加旁白文字，不等于声音场景只能存在于狭窄的逐字朗读间隙。原厂将声音空间、声音入场和表演共同建模。[W01]

因此：

- 保留正文一次且顺序正确。
- 用户明确指定总时长、无前奏、紧凑节奏时遵守。
- 没有明确限制时，不自动禁止必要的非语言声景呼吸或自然节奏。
- 不因此任意加长前奏／尾奏、造成超时或收费增加；仍受本次场景范围、请求数和供应商时长上限约束。

这里不是断言音乐必须依赖长静音才能生成，而是不能把未经用户选择的节奏约束锁进所有scene。

### 2.3 正文整理与声音导演需要分工

原文提取可以保持保守，不增加正文；但不能把“当前固定逐条干声”当作全部声音创作的上位指令。

按实际作用域处理：

- extract：保正文、角色和来源；没有scene意图时照旧，不自动加声景。
- dry director：保持纯人声目标。
- scene director：得到当前完整scene意图、共同指导、采用事件、人物表演和参考观察；围绕已选声景组织，而不是只返回孤立的简短音效条目。
- 已经存在的人工表演不能因切换scene被简单正则删除；必须区分“人声干净”与“整个成品禁止背景”。

最小改造可以先只对scene规划／编译建立独立分支，避免无必要地重写已稳定的extract和dry行为。

### 2.4 scene建议确实缺少一部分用户输入

当前scene分析记录包含unitId、unitRevision、memberIds、existingEvents；发给文本模型的unit为`{id,members}`。`variants.scene.guidance`没有进入这条建议请求。

最终音频输入会读取guidance，所以不能说该要求最终一定丢失。实际问题是：**负责建议场景的AI与负责生成音频的AI看到的上下文不一致。**前者可能不知道用户希望的整体节奏、背景显著性或音乐变化，再给出与它们不匹配的事件。

应补明确快照字段和版本基准，不让模型绕回当前数据库读取不稳定上下文。若本次完全手工设置背景，则绕过此缺口的存在性，不用它替代音频模板A/B。

## 3. N0：建立“用户意图到模型收到什么”的追踪账本（0次模型调用）

### 3.1 固定一份案例，不重新操作到状态漂移

保留本机当前问题音频、音频ID、attemptId、jobId、unitId、模板及引用音色；停止拿同名不同版本相互比较。交接记录为约343字、27秒参考、93.4秒结果。[G01] 由执行者从本机实际文件补齐hash与真实元信息。

不用当前字段反推历史请求：历史音频必须读取**生成时的input和prompt**。若旧记录缺失，明确缺失，不伪造。

### 3.2 七层逐项对照

|层|保存对象|必须回答|
|---|---|---|
|L0 用户原意|用户场景要求、角色和正文，注明人工／已采用AI来源|原本要哪些声音，是否真要求压低、干声、无停顿？|
|L1 UI正式状态|当前unit、scene指导、事件状态与版本、实际音色|编辑是否进入正式状态？是否有草稿未采用？|
|L2 文本AI输入输出|若使用scene建议，保存完整输入及输出关联|整体guidance是否送达？AI是否擅自弱化或撤掉已选声音？|
|L3 音频结构化输入|enhancement形成的不可变input|成员、参考顺序、事件种类／范围和共同指导是否完整？|
|L4 完整编译提示|prompt全文＋逐条来源映射|哪些话是用户，哪些是AI已采用，哪些是系统默认？有何冲突？|
|L5 实際HTTP提交|规范化请求指纹、text_prompt、引用字节hash、模型、路由|所见提示与发送字节是否一致？是否混用input/instructions或偷加参数？|
|L6 原始返回与呈现|供应商原文件hash、应用媒体ID、母版／导出映射|模型原文件是否已有目标背景？后续是否忠实呈现？|

输出`intent-to-wire.md`与`case-manifest.json`。敏感正文、参考Base64、原日志和密钥只留本机；公开报告给脱敏文本和hash。别把Authorization值甚至其可用于攻击的完整记录写入证据。

### 3.3 对默认限制分类，而非全文删词

```text
约束来源：user / inherited_user / adopted_ai / system_default
约束对象：spoken_text / identity / speech_performance / environment / music / scene_pacing
约束文本：实际文字与来源字段
适用范围：dry / scene / both
```

自动处理规则：

- 确认来自旧模板的“事件次要／对白时降低背景／不延长停顿”等偏好，不再继承进新scene模板。
- 正文中出现“不要音乐”等台词，仍然原样朗读；不将它当系统配置。
- 人工写“人声干净”不等于禁止背景；不能一见“干声”就覆盖用户。
- 人工指导真的互相冲突，在同一面板聚合一次，让用户选择哪份意图；不为所有正常scene增加确认。
- 合法的用户轻背景要求必须保留；目标不是全局把背景改为很响。

## 4. N1：同模型、同路由的原生提示对照

### 4.1 为什么必须有“旁路基线”

不能一直通过同一个模板调几个形容词，然后判断模型本身不行。需要同一provider、model、reference、数值配置和正文，用一个**不经过工作台业务模板的完整声景提示**取得对照。

旁路不用于发布新流程：它是受预算约束的诊断脚本，依然向同一个音频生成接口请求一份自带旁白和背景的原生结果，不生成独立背景素材。

### 4.2 冻结的首轮四个条件，各最多两次

选择同一60—100字连续短正文或自拟文本，足够包含两个叙事阶段；相同参考文件字节、同一model与路由，audio_config相同。输出仍是旁白＋已采用环境＋音乐的完整声景。

|条件|提示|发送路径|主要比较|
|---|---|---|---|
|A|当前scene-v2精确提示|工作台正常计划／worker|当前行为基线|
|B|与A规范化请求内容相同|受控旁路直接提交|检查链路是否增加／改变内容；音频不可期待字节相同|
|C|简洁、场景先行的native提示|同一旁路提交|同条件下比较TTS式模板与完整声景指挥|
|D|与C请求内容相同|工作台实验scene编译路径|验证工具能无隐性限制地送出相同意图|

推荐初次最多8次音频请求，先批准再运行；不自动添加文本请求。顺序交错，保存每次响应，不能只展示最好的一份。输出具有随机性；两次重复是诊断起点，不是统计上证明生产成功率。

D应使用白名单内的实验模板，在现有任务／授权机制中运行；不要给公开前端新增可任意越过验证的裸请求入口。

### 4.3 成功与失败如何归因

- **C/D优于A/B**：支持提示策略／编译组织是重要因素；再做小范围消融，不能直接说某一字句已被单独证明。
- **A与B或C与D提交内容不一致**：先修可确认的传输／序列化差异，不继续付费。
- **请求内容相同但声音不同**：先视为生成随机性或上游因素；不能只按路径标签认定工具削弱模型。查请求ID、账户路由、时点与重复结果。
- **C/D都不符合目标**：尚未建立本接入的成功基线。核对已知成功示例的真实条件、参考形态和供应商模型映射；**不转去本地混音**，也不把模型全能力判死。

### 4.4 最多再四个明确名额，不无限试提示

第一轮有可解释信号后再申请。按证据选择用途，不能一口气承诺全部已检验：

- 当前模板只移除固定降低／禁停顿政策的一组消融；
- 同源参考27秒与8—12秒完整自然语句的对照；
- 在保持音色要求的前提下，验证参考使用说明差异；
- 原343字案例采用获胜原生提示的长输出验证。

首轮8＋追加4是本计划建议上限，不是现有授权、供应商金额封顶或必须花满。无参考诊断仅在用户单独同意后进行，不作为正式结果取消角色音色的理由；参考变化不能与多项提示变化混成单变量结论。

若必须更多调用，提交已执行结果、未决假设和下一次要区分的变量，不让AI后台循环“优化到满意”。unknown保留可能已计费记录，普通继续不重发；已发数据不能因为没有音频就当作免费。

## 5. 原生场景编译器：不是在旧尾巴上继续加强调词

### 5.1 推荐实现

在`templates.mjs`中新增实验实现`scene-v3-native`，独立`compileNativeScene`，而不是继续复用带干声默认政策的`compileUnit`再增加布尔参数。

现有scene-v1／v2及dry模板原文不改、不删除；实际通过后再决定新场景默认是否切换。旧单元要明确切模板，旧音频继续保留；既有审核不能变成“新模板已通过”。

### 5.2 输入合同

沿用已有成员、角色槽位、reference、事件和guidance；可追加小量JSON元数据，无需新增声音轨道／素材表：

```text
sceneIntent:
  originalUserDirection
  adoptedSceneDirection
  sceneScope: 当前单句／对话组
  userPacingConstraints（没有则为空）
  explicitBalanceIntent（没有则不自造ducking政策）
  optionalTransitionCues（见下）

provenance:
  用户指导、已采用AI安排、系统默认、既有人工表演的来源引用
```

这些是语义输入，不是上游API新字段；实际请求仍通过文档支持的`text_prompt`与`references`传达。不能把`sceneIntent`、music_volume或内部元数据未经支持直接发送并宣称生效。

### 5.3 提示组织顺序

1. **整体场景是什么**：旁白、环境、音乐共同构成的音频任务。
2. **已采用声音怎样存在与发展**：环境质感、音乐方向、连续／一次性、明确范围。
3. **人物与参考用途**：引用对应声音身份，按当前表演要求执行；避免把参考的全段表现当作所有声景约束。
4. **精确正文与角色分配**：只保留一份待朗读正文。
5. **简短的文字和范围边界**：不读标题、不改词、不添加未批准角色／独立事件；合法声景内部的自然表达不再被一刀切禁止。

这是一种待测的编译设计，不是“标题在前即保证模型听从”的定律。真正效果由N1控制实验判断。

### 5.4 原生单旁白示例（不是本次私有小说原文）

```text
生成一段发生在山洞中的完整中文旁白声景。
旁白、山洞水滴回响和仙侠配乐在同一次输出中共同呈现。

【声音场景】
山洞里有间歇、能够辨识的水滴声，滴落后的回响体现空间。
仙侠器乐具有可听出的旋律，并随着叙述自然转为宁静。
旁白进行时，水滴环境和音乐仍构成可感知的声景；
不是只在开头或结尾短暂出现，也不是仅剩难辨认的底噪。
旁白字词清楚，其他声音按本场景自然安排。

【旁白声音】
说话者A参考@音频1的声音身份。
本次表演：{{已采用的旁白表演指导}}

【只朗读以下正文一次】
{{exact_original_text}}

【边界】
正文文字和顺序保持不变；标题、说明、参考编号不读出。
只呈现已采用的水滴环境和音乐，不另添对白、角色或无关声效。
{{用户实际给出的节奏／时长／位置限制；没有则不强行补写}}
```

不能把示例里“山洞／仙侠”写死到全部scene。多人时保留稳定槽位与每句归属，把对白轮次约束明确写成**对白之间**的关系；环境和音乐与说话同期存在不属于非法重叠。

### 5.5 音乐“随后转宁静”不应被工具逼成精确时间线

- 用户仅提供总体发展方向，允许模型在该段叙事内自然组织，不强迫用户先选播放头或填毫秒。
- 用户明确指向某句／某词时，用原文中真实存在的短引用、成员ID和必要的出现序号表达给模型；内部保存稳定来源，编译成可理解的自然语言。
- 不按字数比例伪造秒数；也不因当前无逐句时间戳就禁止语义时序指挥。
- “音乐转宁静”属于当前音乐事件的发展，不自动拆成两份音乐素材或两次请求。
- 原厂宣传的对白提示级时序控制，不等于当前网关会回传逐字JSON，也不等于所有声效都达到相同精度。界面不要承诺未经测量的毫秒结果。[W01][W02]

### 5.6 正文、字段和约束冲突检查

只移除／改写可追溯的系统创作默认，不修改正文。对人工指南判断作用对象，不能全文正则删除“干声／降低／停顿”。

场景计划和提示必须保留全部已采用事件及用户全局要求。长提示超过3000字符时，先精简系统重复说明；不能先截掉环境／音乐，也不能静默拆成更多付费请求。仍超限时，在原面板说明实际范围并让用户缩小。

有“背景很轻”与“背景明显”这类真正人工冲突，只聚合一次决定；没有冲突时直接使用，不增加常规人工盖章。

## 6. 场景建议支路补齐：看见用户完整意图

### 6.1 必须传递的场景上下文

在`analysis.start`保存并在`launch`发送：

- 用户当前scene共同指导及其revision；
- 正式采用事件的完整语义与范围；
- 当前成员、角色、实际音色引用与已记录参考声学观察；
- 用户已明确的节奏、响度意图和已有人工表演保护；
- 当前目标为scene，不把`dry`描述误作整个任务。

模型只在这些边界内规划。已采用环境／音乐不应被它重复创建或擅自变成“不需要”；已移除事件不能回来。返回空列表只表示没有新增建议，不表示取消用户已经选好的声景。

### 6.2 不要求每次生成先新增一轮文本调用

如果用户已有明确指导和事件，确定性编译就能形成native提示，不再调用文本模型润色。只有用户主动请求场景建议，或在已授权AI流程里，才使用文本模型；该次文本请求独立计数。

scene规划可以增加“完整场景安排建议”，但不得复制改写正文，实际采用前仍使用当前版本检查。保留人工优先和旧建议过期机制。

### 6.3 分段不能把场景拆散来求模型好生成

fd54207增加了语义拆短，并保护已有scene事件和共同指导的片段。[G04] 该保护应保留。本次343字scene不能被重新extract拆成多条后偷偷反复请求，再拼起来冒充单次原生场景成功。

短样本是诊断夹具，不是对用户现有场景的自动改写。若长输出触及供应商限制，实际说明范围和时长风险；用户明确调整场景边界后才执行。

## 7. 请求与供应商核验：查事实，不发明“原生开关”

### 7.1 当前接入没有显而易见的端点错误

当前worker使用`/v1/audio/speech`并发送`text_prompt`、references、audio_config，这与Kunpo公开接口相符。不能因路径含speech就断言它只支持纯语音，也不能改用chat/completions发送音频生成。[G05][W02]

输出格式和采样率、三项rate=0也不是已证实的背景禁用机制。首次A/B保持这些参数不变，不能凭直觉全删后宣称原因已找到。

### 7.2 实际HTTP快照而非UI提示预览

推荐在测试适配器的最终fetch边界记录：

```text
runId / condition / operationId / attemptId
model / endpoint / accountRouteAlias（不含Key）
textPromptSha256 / textPromptLengthCodePoints
canonicalRequestHash / exactWireBodySha256
referenceIdsInOrder / referenceFileSha256[] / duration[]
audioConfig / template / compilerVersion / userIntentRevision
providerRequestId? / httpStatus / responseType / receivedBytes
originalAudioSha256 / duration / sampleRate / channels
```

直接提交B与A、D与C比较规范化JSON内容；保留prompt空格／换行，不能trim后掩盖变化。JSON键顺序可规范化，参考数组顺序不可排序。真实参考字节要比较，不能只说“音色名称一样”。

记录未知结果时不自动再次发；测试适配器不能绕过任务ID、费用范围和保护。后端收到的新实验模板必须是部署白名单，不开任意前端注入原始请求的新权限面。

### 7.3 同参数仍无成功基线时

拿实际providerRequestId、账户分组／路由、model ID和已知成功示例请求条件核对供应商。官网示例可能使用不同参考或输入长度；先记录差异，不宣布路由造假，也不默认切到另一个型号。

只有用户同意提供新路由／账户与素材授权后，才可以做原厂渠道对照；这仍应是同一Seed模型原生声景，不是更换产品目标。没有证据不能把问题推给供应商，更不能因此转为本地混音。

## 8. 返回后的保真检查

### 8.1 对本次反馈的优先级

交接已经说明直接试听新供应商结果仍不清楚。因此首先调查输入和原生输出。后处理是平行排除项，不把所有工作转向音频转换。[G01]

### 8.2 必须核对的最小链

原WAV → 应用直接试听同audioId → 母版对应区间 → 两种导出。录下每个实际媒体ID和文件hash，不凭按钮标题猜。

当前母版会转48kHz单声道。[G06] 如果原始文件有明显背景而mono后消失，应查声道相位及折叠；修复应忠实保留模型已生成的声音，而不是添加新声音或夸大某层。若原文件本身无目标，则不能只修导出结案。

无需为这一步追加模型请求；原文件和诊断派生文件分开放，原声音不覆盖。原始联合音频没有独立轨，不能用总RMS或停顿能量宣称已准确测到音乐／水滴。

## 11. 听评与关闭标准

每次听评记录条件编号、模板、完整请求指纹、原音频hash、设备与正常收听音量。先让听者自由描述听到了什么，再核对水滴／回响／配乐／转宁静，避免看了提示就认为存在。

关闭本问题须同时达到：

- 供应商原始输出自带用户选择的环境和音乐，不是后期补入；
- 水滴与空间回响、音乐旋律能够辨识，宁静变化符合用户意图；
- 旁白内容和角色正确，字词清楚；
- 从正常界面可以复现所用native编译路径，不只在临时脚本成功；
- 应用试听和导出保留同一原生声音；
- 用户对原案例明确满意。少量听评不转成模型普遍成功率。

当前93.4秒真实原文件未交到云端。本地执行者可立即诊断，不必等待上传；需要审核者复听时，上传获准的原场景WAV及最小必要参考／请求脱敏记录。不要拿新的不同样本替换旧失败而不保留标识。

## 12. 可直接发给执行者

> 本轮不采用独立背景生成、本地混音或音源分离。目标是释放seed-audio-1.0原生联合声景能力，供应商返回的一份原始音频必须自带可辨识背景。
>
> 以fd54207固定基线，先追踪用户意图、场景建议、结构化input、完整prompt、最终HTTP和原始音频。重点处理scene-v2强制降低背景／禁止延长停顿、无关对白默认，以及scene建议未接收全局共同指导的问题；不要把最终scene请求误说成仍有dry尾部禁音乐。
>
> 建立同模型、同路由、同参考、同正文的A—D原生对照；新增scene-v3-native实验编译器，不再用干声骨架叠背景附录。正文、角色、采用范围和费用保护全部保留，正常用户不额外填技术参数。未获新授权前真实调用0；首轮最多8次，必要追加最多4次且逐项说明。
>
> 短样本找到有证据的改进后，再验证原343字任务。保持原始输出、旧模板和历史，不为了效果篡改听评、不偷偷拆场景或换模型。失败继续查输入／路由与已知成功条件，不转成本地混音交差。最终以用户听到正确背景、旁白清楚、应用和导出一致关闭。
