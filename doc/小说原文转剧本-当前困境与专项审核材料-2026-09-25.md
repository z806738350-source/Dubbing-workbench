## 1. 请审核者先看这一结论

**“小说原文 → 完整、可审阅、可明确采用的剧本”尚未通过真实整章验收，是当前核心阻塞项。**

工具已经接通文本模型，短样本能成功，部分模型也能返回整章标注。但目前没有一份本次测试的完整第一章结果，成功走完“全部请求完成 → 全文校验 → 人工审阅 → 明确采用”的闭环。

阻塞不是单一原因：

1. **供应商接口波动**：`gemini-3.8-flash` 在多批请求中出现 HTTP 429；取消工具输出上限后仍然发生。
2. **工具原有适配问题**：固定输出 token 上限曾截断模型结果，返回 JSON 的外层包装也曾被误拒收。这两项已修复。
3. **模型内容错误**：`gemini-3.6-flash` 的整章结果中有两条原文引文被改了字。
4. **工具恢复与校对流程不足**：一次请求失败或一条依据错误，会让整轮草稿失败；界面缺少保留有效部分、定点修正、继续未完成批次的正常入口。
5. **当前分块与上下文策略未经充分验证**：约四千字的章节拆成九次请求，并要求模型处理空白块；分块边界和跨批角色理解可能影响成本、失败概率与语义质量。

希望审核者帮助判断：哪些属于实施偏差，哪些需要调整原设计；最小可交付修复应是什么；怎样通过真实章节与故障用例验证，而不是继续只用短样本证明“接口可调用”。

## 2. 工具目标、职责与边界

### 2.1 期望工作方式

用户按章导入小说，AI 标注旁白、对白、心理独白、说话人及表演建议。程序从原文取得朗读正文，用户校对并确认后，绑定参考声音，调用 Seed Audio 逐条配音，最后试听、返工、合并导出。

当前讨论的是**文本理解和剧本整理**阶段。`gemini-*`、`DeepSeek-*` 是本轮使用的文本分析模型；Seed Audio 是后续音频生成模型。文本分析失败不能据此归因于 Seed Audio。

已有手工片段制作、音频小样和导出检查，不能替代自动整理剧本这一步的验收。此前将基础版本表述为已完成，容易掩盖这一关键环节仍未通过真实整章验收，现明确纠正。

### 2.2 已明确的用户要求

- 忠实有声书整理，不自动改编、不删“他说”等叙述、不重写原文。
- 保留跨章角色档案；角色显示名与稳定身份区分。
- AI 结果先作为草稿，用户明确采用；不覆盖用户当前正式编辑。
- 支持用户输入模型名称，自由更换 Kunpo 提供的模型；当前保存的默认名称仍为 `gemini-3.8-flash`。
- **工具端不设置输出 token 上限，不发送 `max_tokens`，也不保留工具自设输出上限配置。**采用服务商自身规则。
- 用户已授权使用真实 API，并发送《不要乱碰瓷》前两章与提供的参考声音进行付费测试。本轮文本对照只使用了第一章及其短样本，没有发送整本书。

“不设输出 token 上限”不等于取消原文保护、输入校验或自动允许无限重复付费。当前单请求仍有 180 秒等待超时；它与输出 token 上限是不同参数，是否适配慢模型应单独评估。

## 3. 当前真实实现，便于定位问题

### 3.1 数据流

```text
已保存章节原文 + 当前章节可用角色档案
    ↓
程序切分原文块，分配块 ID 和原文区间
    ↓
按块数/字符数分批，逐批调用文本模型
    ↓
每批解析 JSON，检查块覆盖顺序和完整性
    ↓
全部批次结束后，统一检查角色、字段和原文出处
    ↓
全部通过 → ready 草稿 → 用户确认替换 → 事务内应用
任一步出错 → failed → 当前正式剧本不变
```

此处 `ready` 只表示具备审阅和采用资格，不代表角色和表演判断已被人工验收。

### 3.2 分块与上下文

| 项目 | 当前实现 |
|---|---|
| 原文坐标 | 以 Unicode 码点计数，保存左闭右开 `start/end` |
| 切块方式 | 中文开引号之前切；中文闭引号、换行之后切；连续约 251 个码点也切 |
| 每批规模 | 最多 24 个块，或块正文累计约 1200 字符；后者使用 JavaScript 字符串长度 |
| 模型返回范围 | `from/to` 是本批局部块 ID，闭区间；程序再换算到全章块 ID |
| 覆盖要求 | 当前实现要求本批每个块恰好一次，包含纯空白块 |
| 角色上下文 | 截至本章可用的角色 ID、名称、别名、事实；过滤后续章节来源 |
| 跨批上下文 | 当前批之前最多两个原文块；不额外提供后续块作为上下文 |
| 新角色延续 | 提供前批新角色名称集合 `knownNames`，没有同步传递完整的临时角色描述和证据 |
| 发送方式 | 一个分析任务内部串行；没有任务内自动重试或逐批退避 |

第一章实测：**4,446 个 Unicode 码点，203 个原文块，54 个纯空白块，9 批请求。**

这些数字来自本轮保存的第一章和当前切块函数，不是对小说所有章节的统计。原文块数也不等于最终配音片段数。

### 3.3 当前请求与结果字段

接口路径为 `/v1/chat/completions`。当前请求主要字段：

```json
{
  "model": "用户本次选择的模型名称",
  "messages": [
    { "role": "system", "content": "忠实标注、覆盖规则、角色与表演指导、JSON 输出要求" },
    { "role": "user", "content": "序列化后的角色、原文块、前文与已发现名称" }
  ],
  "temperature": 0.2,
  "response_format": { "type": "json_object" }
}
```

示意返回结构（不是某次响应原样）：

```json
{
  "items": [{
    "from": 0,
    "to": 2,
    "roleId": null,
    "newRole": "新角色名",
    "type": "dialogue",
    "performance": "轻声、犹豫",
    "evidence": "原文明示",
    "sourceQuote": "模型复制的原文依据",
    "reason": "说明判断理由",
    "uncertain": false
  }]
}
```

实际朗读 `text` 由程序按原文块拼接，**不采用模型重新写出的台词**。但依据 `sourceQuote` 目前仍由模型重新复制，这与正文保真的处理方式不同。

### 3.4 校验、保存和界面行为

- 每批立即检查 `from/to` 的顺序、重复、越界和尾部遗漏。
- 内容类型、角色 ID、表演字段、依据类别和出处，在全部批次结束后才统一校验。
- `evidence = 原文明示` 时，当前检查为 `sourceQuote` 非空且是整章原文的连续子串。
- 这能发现引文改字，但**不能证明引用支持该条角色或表演判断**；同一短句在原文多次出现时，也没有明确定位到哪一次。
- 一条出处失败即抛错，整份草稿变成 `failed`；不会自动把其余条目变为可审阅结果。
- 批次循环中的累计结果主要保存在进程内 `items`。`record.rawItems` 直到全部批次完成后才写入。
- 中途 HTTP 失败时，记录里有进度、已成功调用的部分统计和最后响应内容，但没有按批完整持久化的累计标注及请求上下文；不能据此直接实现可靠续做。
- 如果九批都完成、最后内容校验失败，`rawItems` 已保存。例如 3.6 的 107 条结果仍在诊断记录中，但 `record.items` 为空，正常界面无法逐条修正这些结果。
- 界面主要显示最后一轮草稿。提取草稿是只读预览后整份确认替换；当前没有失败条目的编辑器、按批继续入口或局部修复入口。
- 明确采用时仍检查章节编辑修订、项目上下文修订和可编辑状态，在事务中写入。正式旧片段保留为历史，原音频不被直接删除。
- 提取结果采用时按 `newRole` 名称精确归并本轮新角色，不自动将不同名称判断成同一人；`roleConfirmed` 使用模型的 `!uncertain`。是否需要更保守的人机确认规则，请审核。

## 4. 真实测试经过与结果

### 4.1 实验范围与可信度

使用正式分析代码和隔离数据库副本，保持第一章原文、角色上下文、提示词与分块规则一致，依次测试模型。诊断修复后复用此前完整响应，继续尚未成功部分，避免重复付费。

因此“九批返回”是**保存响应的重放加后续真实请求的组合验证**，不能写成一次全新独立的九批成功。重放工具仅用于本轮诊断，不能当作产品已经具备断点恢复功能。

本次编写文档只核对代码、设计文件和已保存响应，没有新增模型调用。上轮 29 项自动检查与生产构建已通过；自动检查不能代替真实整章质量验收。没有获取供应商账单，不报告实际费用金额。

### 4.2 gemini-3.8-flash：取消上限仍发生 429

较早整章测试完成 4/9 批后收到：

```json
{
  "error": {
    "message": "Resource exhausted. Please try again later. ...",
    "type": "rate_limit_error"
  }
}
```

用户提出输出上限可能导致失败后，用同一批输入做正序、倒序对照：

| 顺序 | 唯一参数差异 | 结果 | 耗时 |
|---|---|---|---|
| 1 | `max_tokens = 5000` | HTTP 429 | 0.7 秒 |
| 2 | 不传 `max_tokens` | HTTP 200 / stop，覆盖检查通过 | 9.6 秒 |
| 3 | 不传 `max_tokens` | HTTP 200 / stop，覆盖检查通过 | 9.0 秒 |
| 4 | `max_tokens = 5000` | HTTP 200 / stop，覆盖检查通过 | 4.4 秒 |

随后运行不传上限的整章流程：复用第一批成功响应，第 2—5 批真实调用成功，**第 6 批仍返回 HTTP 429，停在 5/9**。

可确认：不是每次调用都失败；取消工具上限并不能消除 429。不能确认：429 究竟来自账号配额、共享模型通道、容量还是其他上游限制。没有供应商内部日志，也不能据此判断 API Key 无效或余额不足。

### 4.3 gemini-3.6-flash：返回整章但两条引文失真

1. 原上限 5000：前两批通过；第三批 HTTP 200，但返回顶层数组，旧解析流程拒收。
2. 兼容数组后复用前三批：第四批返回 `finish_reason: length`，JSON 被截断；统计含 4113 个推理 token、880 个文本 token。
3. 将该批上限提高到 10000 对照：返回完整内容，但 JSON 外包单反引号，旧包装处理拒收。
4. 兼容包装后复用前四批：后五批真实请求成功，合计九批、107 条标注，全章块覆盖校验通过。
5. 最终检查发现两条“原文明示”引文不在原文中，整轮失败。

具体差异：

| 来源 | 文本 |
|---|---|
| 模型依据引文 | 叶素回头，脸上的笑淡了**起来**： |
| 实际原文 | 叶素回头，脸上的笑淡了**下来**： |

需要区分：**已确认的错误发生在依据引文，不是程序重建的朗读正文被模型改写。**当前规则将这类局部依据错误升级成了整份草稿失败。

附加观察：107 条标注中，11 条只覆盖空白，`uncertain=true` 为 0；新角色名同时包含“轻甜女声”“宁浅瑶”等。这里不预先认定哪些名称一定指同一个人，也不将零疑点标记视为角色判断全部正确。这提示还需要人工角色与别名审阅，覆盖检查本身无法完成语义验收。

### 4.4 DeepSeek-V4-Pro：短样本可用，复杂输入未完成

| 测试 | 结果 | 耗时 |
|---|---|---|
| 与其他模型相同的第一批，5000 上限 | HTTP 200 / length；正式内容为空，仅有推理；输出用尽 | 80.3 秒 |
| 同一批，10000 上限 | HTTP 200 / length；正式内容仍为空；输出用尽 | 164.5 秒 |
| 缩至第一章标题和开篇两段，10000 上限 | HTTP 200 / stop；1 条标注，覆盖检查通过；输出 2047 token | 31.6 秒 |

该模型路由不是完全不可调用，但**尚未完成取消工具上限后的复杂输入及整章验证**。不能将旧上限下的失败写成当前无上限实现必然失败，也不能假设去掉上限就一定成功。

响应中的模型标识为 `vanchin/deepseek-v4-pro-0813`；这是 Kunpo 返回值，未独立核验底层模型身份。

## 6. 设计基线与实现之间的关键差距

### D01：方案要求保留有效草稿，目前实现是整轮失败

主方案第 3.1 节已有明确要求：

> 有问题时保留有效草稿和原文，指出具体缺口，不接受成“完整剧本”。

当前实现确实没有把缺陷结果当成完整剧本，但**保留、展示、修正有效草稿这一半没有充分落实**。因此应先判断能否在既有规则下补齐实现，而不是将它描述成必须重写整份产品设计。

### D02：方案支持块／区间出处，代码却依赖模型抄写引文

写作规范第 3.4 节要求“原文明示使用有效的文本块／区间引用”。当前实现让模型输出 `sourceQuote`，再做字符串包含检查，增加了抄写错误与重复短句定位问题。

请审核：是否应该让模型选择依据块 ID 或程序提供的边界，再由程序显示依据原文；需要精确到块内时，如何避免要求模型自行数长文本坐标？这可能比继续加强“请逐字复制”的提示更直接，但尚未实现。

### D03：方案优先完整章理解，代码固定做小批标注

主方案第 3.2 节要求优先在模型可承载范围内理解完整章节。当前四千余字就固定分九批，没有先取得全章理解结果，也未做整章与分批的公平对照。

较小请求可能降低单次输出复杂度，但请求次数增加会增加中途失败机会；较少上下文可能损害说话人和别名判断。应依据实际数据权衡，不能把“越小越稳”当作已经验证的结论。

### D04：空白块校验比设计中的正文覆盖要求更严格

主方案要求覆盖应朗读的非空白内容。当前提示词要求模型显式覆盖空白块，而采用时又过滤纯空白条目。

请审核是否可由程序保留空白与坐标映射，让模型主要标注有语义的块，减少无意义输出。任何调整仍必须保留正文顺序和原文定位，不能因此漏掉有效文字。

### D05：角色判断、表演建议和依据被放在同一条强校验路径

当前单个 `evidence/sourceQuote/reason` 与角色、类型、表演一起返回，依据到底对应哪项判断并不够清晰。任一依据错误都会阻止整个剧本进入审阅。

请审核是否应该区分：正文结构错误、角色身份待确认、可选表演建议缺陷。区分不意味着静默放行；重点是让用户明确看到问题，并知道哪些内容仍不能采用或生成。

## 7. 希望审核者比较的改进方向

以下是候选方向，不是已经选定的实现方案。请优先给出能够在当前 React + Node + SQLite 结构中落地的最小改动，说明取舍。

| 候选方向 | 可能解决的问题 | 必须回答的边界问题 |
|---|---|---|
| 按批持久化输入、原始响应与校验结果 | 中途失败不丢有效工作；可以追溯和恢复 | 章节或角色上下文变化后，哪些结果还能复用？如何避免自动重复计费？ |
| 保留带问题的草稿，增加局部修正入口 | 一条引文错误不必重做整章 | “可查看”“可修正”“可采用”如何区分？缺口能否被用户误当完整稿？ |
| 依据改用原文块／区间引用 | 避免模型重新抄写引文 | 引用跨批前文怎么办？重复文本如何定位？引用合法但语义不支持时怎么办？ |
| 将必需的结构与角色标注同可选表演建议分开 | 可选建议失败不阻断基础剧本 | 是否增加总请求和时延？角色仍不确定时如何阻止误配音？ |
| 整章理解或更大语义分块 | 减少请求次数、提高身份理解连续性 | 如何控制响应复杂度、定位缺口、保留局部恢复能力？ |
| 程序处理纯空白，模型只负责有语义的块 | 减少无意义标注与 token 消耗 | 如何保留原文坐标、标点和相邻片段边界？ |
| 明确触发的局部重新分析或换模型 | 恢复失败部分 | 混合模型结果如何保持角色一致？已有效的其他部分是否需要失效？ |
| 对明确可重试错误做有限退避 | 降低瞬时 429 的影响 | 哪些响应确定适合重试？超时结果不明怎么办？不要把所有失败都当成可安全重发 |

当前两批之间存在 `knownNames` 的依赖，因此“只重跑某一批”并不天然独立。如果修正前批后改变了角色判断，需要说明后续批次如何重新核对，不能只按批号拼起来。

也不建议自动把无效“原文明示”改成“上下文推断”后放行。那会改变模型建议的依据性质，若采用此类降级路径，应明确展示并由用户决定。

## 8. 请审核者给出具体答复的问题

1. 是否认可 D01—D05 的判断？哪些是代码实现偏离既有方案，哪些确实需要修订业务规则？

4. 四千余字章节是否适合整章处理？若分块，应按什么边界、携带多少上下文？请给出可验证的比较方法。

9. 是否需要调整 180 秒等待时间、串行节奏或模型请求格式？需要哪些实际证据才能决定？请不要重新引入工具端固定输出 token 上限。

## 9. 建议的验收场景（待审核，不是已通过）

| 编号 | 场景 | 希望确认的结果 |
|---|---|---|
| A01 | 第一章完整提取 | 原文覆盖完整，可审阅、校对并明确采用，来源可追溯 |
| A02 | 含不同对话结构的第二章 | 不只针对第一章调参；已确认角色可延续，新疑点可定位 |
| A03 | 第六批模拟 429 | 前五批有效工作可保留；正式剧本不变；恢复不重复请求无关已完成部分 |
| A04 | 已完成草稿有两条无效依据 | 明确定位两条问题，允许按批准的规则局部修正，不需要全章重做 |
| A05 | 缺漏、重复、越界 | 具体显示缺陷，不能作为完整剧本采用；不靠模糊匹配隐藏问题 |
| A06 | JSON 外层包装变化 | 对象、数组、代码块或单反引号包装可解析，内部损坏仍拒绝 |
| A07 | 分析期间编辑原文或角色资料 | 旧结果不覆盖新编辑；复用和重跑范围明确 |
| A08 | 前批角色归属修正 | 后批依赖可核对，不静默保留矛盾身份，不擅自合并角色 |
| A09 | 进程重启或连接中断 | 已保存工作可找回，结果不明的请求不自动重复付费 |
| A10 | 纯空白、引号、长段和 Unicode 字符 | 正文与坐标保持一致，分块边界不导致文字遗漏或重复 |
| A11 | 同一句话在原文出现多次 | 引文能定位到具体出处，而非仅通过全章字符串包含检查 |
| A12 | 模型所有条目都声称确定 | 界面仍能支持人类发现和纠正说话人、别名、心理独白错误 |
| A13 | 模型选择与请求参数 | 使用用户选择的模型，不静默切换，不发送工具输出上限 |
| A14 | 应用修正后的完整草稿 | 采用为一个受修订检查保护的操作，失败不留下半份正式剧本 |

验收报告应分别记录：请求是否完成、结构是否完整、角色语义是否正确、表演建议是否可用、用户是否采用。不要用单一“成功率”混合这些指标。
